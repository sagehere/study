# Knowledge Types

Use the narrowest type that matches the main learning difficulty.

## procedural
Use when the learner must execute and monitor a procedure, not merely recognize a concept. Typical structure:
`diagnose → guided → repair → formalize → independent → transfer → complete`

Design emphasis: decision points, verification, adjustment, worked-example fading, and fresh variants after strong help. Example family: trial quotient and adjustment.

## concept-representation
Use when the learner must distinguish mathematical objects/quantities and connect representations before formulas. Typical structure:
`diagnose → contrast → repair → representation → formalize → transfer → complete`

Design emphasis: boundary vs surface, concrete/visual/abstract bridges, same-number/different-quantity conflicts, language and unit meaning. Example family: perimeter vs area.

## quantity-relation
Use when the main work is identifying roles in a multiplicative/additive model and switching unknowns. Typical structure:
`diagnose → model → repair → inverse → formalize → composite → transfer → complete`

Design emphasis: “per one” meaning, unit rate, inverse relations, unknown-role changes, composite situations, intermediate quantities. Example family: unit price × quantity = total price.

## boundary-concept
Use when a rule is best understood through positions, thresholds, intervals, or inclusivity at a boundary. Typical structure:
`locate → boundary → repair → formalize → reverse → transfer → complete`

Design emphasis: location before mnemonic, exact threshold cases, left/right inclusivity, magnitude checks, and reverse interval reasoning. Example family: rounding on a number line.

## If none fits
Do not silently invent a new runtime type. Describe the missing pedagogical capability, identify whether the current Flow Engine can still express it with existing steps/effects/renderers, and flag any renderer or DSL extension separately.
